# R2: Backend lead

## Mission

Own the shared contracts, the backend pipeline (stages 02 through 07), the runner,
tests, and docs. You are the integration point: everything flows through your code.

## Folder you own

`contracts/`, `backend/app/ingestion/`, `backend/app/pipeline/`, `backend/app/fusion/`,
`backend/app/response/`, `backend/app/evidence/`, `ml/runner/`, `tests/`, `docs/`. You
may not edit any other folder. You are the only person who edits `contracts/`.

## What makes your role different

- You own `contracts/` and review all PRs that touch shared interfaces.
- You answer `QUESTIONS.md` once a day.
- You run R1's model against held-out data and report the number, so the model author
  is not also the evaluator.
- You review every PR, not just contract PRs.

## Start here

Paste this into your coding agent:

```
I am the backend lead for SATYACHECK. I own contracts/, backend/app/ (ingestion,
pipeline, fusion, response, evidence), ml/runner/, tests/, and docs/.

Read these files first, in order: AGENTS.md, docs/interfaces.md,
contracts/acquisition.py, contracts/pipeline.py, contracts/checks.py,
contracts/context.py, contracts/risk.py, contracts/evidence.py,
tests/test_contracts_smoke.py, tests/test_transport_invariant.py.

My build order:
1. Stages 02 (ingestion) and 03 (pipeline) first. Ingestion receives AudioChunk from
   either Exotel or WebRTC, decodes the codec, normalizes to CanonicalAudioChunk (16
   kHz mono s16le, 640 bytes per frame). Pipeline buffers into CanonicalAudioBatch
   windows with silence filtering. Stage 03 budget: under 20 ms.
2. Hold the pipeline stable while R1 swaps model implementations in.
3. Stage 05 fusion: combine the four check signals with CallContext into a 0-100
   score. Budget: under 30 ms. Two rules that must hold: never trigger on a single
   instantaneous score (require sustained risk across windows or one high-severity
   event), and thresholds must be configurable per deployment.
4. Stage 06 response: dispatch RiskUpdate to the app over WebSocket. Budget: under
   50 ms. The app contract is AppMessage (discriminated union of SessionStart,
   RiskUpdate, CallEnded on kind).
5. Stage 07 evidence: fingerprint each alert event, fold into Merkle tree, publish
   root off-ledger. AlertRecord, SealedRecord, ChainAnchor are the shapes.
6. Evaluation harness: run R1's models against held-out data, report metrics.

The transport invariant: nothing below stage 02 may import or branch on which
transport (exotel or webrtc) delivered the audio. CanonicalAudioChunk and
CanonicalAudioBatch carry no transport, codec, or sample_rate field. The invariant
test at tests/test_transport_invariant.py enforces this with an AST walk.

Check runner: implements CheckRunner protocol from contracts/checks.py. Fans out to
all four checks in parallel on a COPY of the batch, enforces 180 ms deadline,
marks stragglers FAILED or SKIPPed, returns ChecksBatchResult.

RiskUpdate fields: kind ("risk_update"), stream_id, call_id, sequence, timestamp,
score (0-100), verdict (RiskVerdict), risk_level (RiskLevel), confidence (0-1),
reasons (list[ReasonCode]), contributing_checks, degraded_checks, evidence_refs
(opaque ids only), schema_version ("1.0").

DEFAULT_BAND_MAPPING: 0=low, 40=medium, 70=high, 90=critical. The app renders
RiskLevel; it never computes a band from score.

Do not add dependencies without asking. Do not commit real audio, voiceprints, .env,
keys, or evaluation data. Show a plan before writing any code.
```

## Self-check

1. `uv run pytest tests/test_contracts_smoke.py -q` - all 8 tests pass.
2. `uv run pytest tests/test_transport_invariant.py -q` - both tests pass.
3. After adding ingestion code, verify no transport import leaked:
   `uv run pytest tests/test_transport_invariant.py -q` must still pass.
4. After adding fusion code, write a test that feeds four CheckResult objects and a
   CallContext into the fusion function and asserts the output is an int between 0
   and 100. Run it.
5. After adding evidence code, write a test that fingerprints an AlertRecord and
   verifies the fingerprint is a 64-character hex string (sha256). Run it.
6. After adding response code, write a test that constructs an AppMessage and
   serializes it to JSON. Verify round-trip: deserialize and check all fields match.
7. After adding the runner, write a test that calls run_checks with a mock batch and
   verifies ChecksBatchResult has one CheckResult per CheckName. Run it.

## If you are blocked

1. Try: re-read `docs/interfaces.md` section 3 (message schemas). The field you
   need is documented there.
2. Try: check if the contract type exists by importing it:
   `uv run python -c "from contracts.risk import RiskUpdate; print('ok')"`
3. If still blocked, you are R2. You answer your own questions by reading the
   contracts. If the contract is genuinely missing something, document the gap in
   `docs/interfaces.md` and move on.
4. While waiting, switch to: test coverage for existing code, or the evaluation
   harness setup.

## Never

- Do not edit files outside your folders.
- Do not weaken, skip, or xfail a test to make a suite pass. Report the failure.
- Do not commit real audio, voiceprints, `.env`, keys, or held-out evaluation data.
- Do not let a transport import leak below stage 02. The invariant test catches it,
   but do not rely on the test alone.
- Do not ship a fusion function that triggers on a single instantaneous score.
- Do not hardcode threshold values that should be per-deployment configurable.
